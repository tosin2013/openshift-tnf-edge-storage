= Module 5: Disaster Recovery
:navtitle: 5. Disaster Recovery

== Introduction

LINSTOR provides crash-consistent snapshots that can be shipped to an S3-compatible object store.
Subsequent snapshots ship only the *changed blocks* (incremental deltas), making remote backup bandwidth-efficient -- a critical property for edge sites with limited uplinks.

In this module you will configure an S3 remote, take snapshots of the database PVC, and verify incremental delta shipping.

== Step 1: Configure the S3 Remote

[tabs]
====
MinIO (Default)::
+
Deploy a MinIO instance as an S3-compatible endpoint for the lab:
+
[source,bash,role=execute,subs="attributes+"]
----
cat <<'MEOF' | oc apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: minio
  namespace: {workshop_namespace}
  labels:
    app: minio
spec:
  replicas: 1
  selector:
    matchLabels:
      app: minio
  template:
    metadata:
      labels:
        app: minio
    spec:
      containers:
        - name: minio
          image: quay.io/minio/minio:latest
          args: ["server", "/data"]
          env:
            - name: MINIO_ROOT_USER
              value: minioadmin
            - name: MINIO_ROOT_PASSWORD
              value: minioadmin
          ports:
            - containerPort: 9000
---
apiVersion: v1
kind: Service
metadata:
  name: minio
  namespace: {workshop_namespace}
spec:
  selector:
    app: minio
  ports:
    - port: 9000
      targetPort: 9000
MEOF
----
+
Wait for MinIO to be ready, then create the backup bucket:
+
[source,bash,role=execute,subs="attributes+"]
----
oc wait --for=condition=available deploy/minio -n {workshop_namespace} --timeout=120s
oc exec -n {workshop_namespace} deploy/minio -- mc alias set local http://localhost:9000 minioadmin minioadmin 2>/dev/null || true
oc exec -n {workshop_namespace} deploy/minio -- mc mb local/workshop-backups 2>/dev/null || true
----
+
Create the LINSTOR remote pointing to MinIO:
+
[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor remote create s3 --use-path-style \
  workshop-dr-target \
  http://minio.{workshop_namespace}.svc:9000 \
  workshop-backups \
  us-east-1 \
  minioadmin \
  minioadmin
----

AWS S3::
+
If you have an AWS S3 bucket, create the LINSTOR remote pointing to it:
+
[source,bash,role=execute,subs="attributes+"]

  linstor remote create s3 \

  https://s3.amazonaws.com \

  <your-region> \
  <your-access-key> \
  <your-secret-key>
----

Verify the remote was created:

[source,bash,role=execute,subs="attributes+"]

oc exec -n {linbit_namespace} deploy/linstor-controller -- linstor remote list
----

== Step 2: Create an Encryption Passphrase

LINSTOR requires a master encryption passphrase before S3 remotes can be created (credentials are encrypted at rest):

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor encryption create-passphrase --passphrase workshop-lab-2024
----

NOTE: In production, use Vault or an external KMS for passphrase management.

== Step 3: Take the First Snapshot

Identify and capture the LINSTOR resource name backing the database PVC:

[source,bash,role=execute,subs="attributes+"]
----
export LINSTOR_RESOURCE=$(oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor resource list --output-format json | python3 -c "
import sys, json
for r in json.load(sys.stdin).get('resource_states', json.load(open('/dev/stdin')) if False else []):
    pass
" 2>/dev/null || \
  oc get pv $(oc get pvc -n {workshop_namespace} -l app=sample-db -o jsonpath='{.items[0].spec.volumeName}') \
    -o jsonpath='{.spec.csi.volumeAttributes.linstor\.csi\.linbit\.com/resource-group}' 2>/dev/null || echo "")
----

If the above does not capture automatically, list resources and set manually:

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- linstor resource list
----

[source,bash,role=execute,subs="attributes+"]
----
# Set the resource name from the output above
export LINSTOR_RESOURCE=<resource-name-from-output>
----

Take a snapshot:

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor snapshot create ${LINSTOR_RESOURCE} snap-baseline
----

== Step 4: Ship the Snapshot to S3

Ship the baseline snapshot to the remote target:

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor backup create workshop-dr-target ${LINSTOR_RESOURCE}
----

Verify the backup was created:

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor backup list workshop-dr-target
----

Note the backup ID and size -- this is a *full* backup.

== Step 5: Generate New Data

Write additional data to the database to create a delta:

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {workshop_namespace} sample-db-0 -- \
  psql -U demo -d workshop -c "
    CREATE TABLE IF NOT EXISTS dr_test (id serial PRIMARY KEY, payload text, created_at timestamp DEFAULT now());
    INSERT INTO dr_test (payload) SELECT md5(random()::text) FROM generate_series(1, 10000);
  "
----

Verify the data was inserted:

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {workshop_namespace} sample-db-0 -- \
  psql -U demo -d workshop -c "SELECT count(*) FROM dr_test;"
----

== Step 6: Take an Incremental Snapshot

Take a second snapshot and ship it:

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor backup create workshop-dr-target ${LINSTOR_RESOURCE}
----

List backups again:

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor backup list workshop-dr-target
----

Compare the sizes:

* The *first* backup is a full copy of the volume
* The *second* backup ships only the *blocks that changed* since the first snapshot

This incremental approach dramatically reduces bandwidth requirements for remote DR from edge sites.

== Step 7: Discussion

Consider these disaster recovery scenarios:

* *Site loss:* How would you restore from S3 into a new cluster?
** Use `linstor backup restore` on the recovery cluster, pointing to the same S3 remote
** Schedule the pod on the restored volume -- data as of the last incremental snapshot

* *RPO (Recovery Point Objective):* How often should you ship snapshots?
** Block-level deltas are small -- hourly or even more frequent shipping is practical at the edge

* *Encryption:* Why encrypt backup data in S3?
** S3 buckets may be in a different security zone; encryption-at-rest prevents data exposure

== Clean Up

Remove the test table:

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {workshop_namespace} sample-db-0 -- \
  psql -U demo -d workshop -c "DROP TABLE IF EXISTS dr_test;"
----

Remove the snapshots (optional -- they do not affect the running cluster):

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor snapshot delete ${LINSTOR_RESOURCE} snap-baseline
----
