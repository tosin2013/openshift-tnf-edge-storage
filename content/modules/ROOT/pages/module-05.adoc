= Module 5: Disaster Recovery
:navtitle: 5. Disaster Recovery

[sidebar]
****
*Duration:* 45 minutes +
*Objective:* Configure and execute incremental S3 snapshot shipping for geographic disaster recovery.

== Introduction

LINSTOR provides crash-consistent snapshots that can be shipped to an S3-compatible object store.
Subsequent snapshots ship only the *changed blocks* (incremental deltas), making remote backup bandwidth-efficient -- a critical property for edge sites with limited or metered uplinks.

In this module you will:

* Deploy a MinIO instance as an S3-compatible endpoint
* Set up LINSTOR encryption and configure an S3 backup remote
* Take a full baseline snapshot and ship it to S3
* Generate new data, ship an incremental backup, and compare the dramatic size difference
* Discuss RPO, restoration, and encryption considerations for edge DR

== Step 1: Set Up Encryption

LINSTOR encrypts S3 remote credentials at rest, so a master encryption passphrase must be configured *before* creating any S3 remote.

Create the passphrase (if this is the first time) or enter it (if it already exists):

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor encryption create-passphrase --passphrase workshop-lab-2024 2>&1 \
  || oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor encryption enter-passphrase --passphrase workshop-lab-2024
----

.Sample output (first time)
[%collapsible]
====
[source,text]
----
SUCCESS:
    Crypt passphrase created
----
====

.Sample output (passphrase already exists)
[%collapsible]
====
[source,text]
----

Description:
    Could not create new crypt passphrase as it already exists
...
SUCCESS:
    Passphrase accepted
----
====

NOTE: In production, use Vault or an external KMS instead of a static passphrase.

== Step 3: Identify the LINSTOR Resource and Take a Snapshot

In LINSTOR, the PersistentVolume name *is* the resource name. Extract it from the database PVC:

[source,bash,role=execute,subs="attributes+"]
----
export LINSTOR_RESOURCE=$(oc get pvc data-sample-db-0 -n {workshop_namespace} \
  -o jsonpath='{.spec.volumeName}')
echo "LINSTOR resource: ${LINSTOR_RESOURCE}"
----

.Sample output
[%collapsible]
====
[source,text]
----
LINSTOR resource: pvc-542487aa-2a4e-43ef-a156-e3b8d45e8e2a
----
====

Take a crash-consistent snapshot (the delete command ensures idempotency if you re-run this module):

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor snapshot delete ${LINSTOR_RESOURCE} snap-baseline 2>/dev/null || true
oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor snapshot create ${LINSTOR_RESOURCE} snap-baseline
----

.Sample output
[%collapsible]
====
[source,text]
----
SUCCESS:
Description:
    New snapshot 'snap-baseline' of resource 'pvc-542487aa-...' registered.
    ...
SUCCESS:
    Took snapshot of '[pvc-542487aa-...]' on 'ip-10-0-1-10'
SUCCESS:
    Took snapshot of '[pvc-542487aa-...]' on 'ip-10-0-1-11'
    ...
SUCCESS:
    Resumed IO of '[pvc-542487aa-...]' on 'ip-10-0-1-10' after snapshot
----

Notice that LINSTOR briefly suspends I/O, takes the snapshot on each replica node, then resumes -- the entire operation typically completes in under a second.
====

== Step 6: Ship an Incremental Backup and Compare

Take a second backup and ship it. LINSTOR automatically detects the previous backup and ships only the changed blocks:

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor backup create workshop-dr-target ${LINSTOR_RESOURCE}
----

Wait for it to complete, then list both backups:

[source,bash,role=execute,subs="attributes+"]
----
sleep 15
oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor backup list workshop-dr-target
----

[IMPORTANT]
.Incremental Delta in Action
====
|===
| Backup | Type | Size

| `back_..._212328` | Full (baseline) | **38 MiB**
| `back_..._212410` | Incremental (after 10k rows) | **684 KiB**
|===

The incremental backup is *98% smaller* than the full backup -- only the changed blocks from inserting 10,000 rows were shipped. For edge sites with limited bandwidth (satellite, metered cellular), this delta-only model makes frequent DR backups practical.
====

== Step 7: Discussion

Consider these disaster recovery scenarios:

* *Site loss:* How would you restore from S3 into a new cluster?
** Deploy LINSTOR on the recovery cluster and configure the same S3 remote
** Run `linstor backup restore workshop-dr-target <resource-name>` to download the latest snapshot chain
** Schedule the pod on the restored volume -- data is as of the last shipped backup

* *RPO (Recovery Point Objective):* How often should you ship snapshots?
** Block-level deltas are small (our test showed 684 KiB for 10k rows of changes)
** Hourly or even more frequent shipping is practical at the edge
** LINSTOR snapshots are crash-consistent so there is no need to quiesce the application

* *Backup chain management:* What happens as the chain grows?
** Each incremental backup depends on its parent. Periodically taking a fresh full backup (by deleting old snapshots first) prevents long restore chains.
** Use `linstor backup delete` to prune old backups from S3

* *Encryption:* Why encrypt backup data in S3?
** S3 buckets may be in a different security zone; encryption-at-rest prevents data exposure
** LINSTOR encrypts remote credentials at rest (the passphrase you configured in Step 1)

== Clean Up

Remove the test data:

----
oc exec -n {workshop_namespace} sample-db-0 -- \
  psql -U workshopuser -d workshop -c "DROP TABLE IF EXISTS dr_test;"

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor snapshot delete ${LINSTOR_RESOURCE} snap-baseline 2>/dev/null || true
----

List and delete the backup snapshots:

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- linstor snapshot list
----

Delete each backup snapshot shown in the output:

[source,bash,role=execute,subs="attributes+"]
----
for SNAP in $(oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor -m snapshot list 2>/dev/null | python3 -c "
import sys, json
data = json.load(sys.stdin)
for snap in data:
    for s in snap.get('snapshot_dfns', []):
        name = s.get('snapshot_name', '')
        if name.startswith('back_'):
            print(name)
" 2>/dev/null); do
  echo "Deleting snapshot: $SNAP"
  oc exec -n {linbit_namespace} deploy/linstor-controller -- \
    linstor snapshot delete ${LINSTOR_RESOURCE} "$SNAP"
done
----

Remove the S3 remote, MinIO deployment, and service:

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- \
  linstor remote delete workshop-dr-target
oc delete deploy/minio svc/minio -n {workshop_namespace}
----
