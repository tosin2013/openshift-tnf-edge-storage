= Module 1: Storage Foundations
:navtitle: 1. Storage Foundations

[sidebar]
****
*Duration:* 30 minutes +
*Objective:* Understand LINSTOR/DRBD architecture and verify the storage layer on your cluster.
****

== Introduction

LINBIT SDS separates the *control plane* (LINSTOR Controller) from the *data plane* (DRBD kernel module running on each satellite node).
The Controller manages resource definitions, storage pools, and scheduling.
DRBD handles block-level replication with in-kernel efficiency -- no userspace I/O overhead.

Your student cluster uses a *Two-Node with Arbiter (TNA)* topology -- the standard edge deployment pattern:

[cols="1,1,2"]
|===
| Role | Count | Function

| *Primary node*
| 2
| Runs workloads and holds diskful DRBD replicas on local EBS storage.

| *Arbiter node*
| 1
| Lightweight node that participates in DRBD quorum votes but stores no data.
Breaks ties when one primary goes down, preventing split-brain.
|===

This gives you the resilience of 3-way replication at the cost of only 2 full storage nodes -- a practical trade-off for edge sites where hardware is limited.

In this module you will explore the running LINSTOR deployment and see how storage pools, diskful replicas, and the diskless arbiter map to this topology.

== Step 3: Inspect Storage Pools

View the storage pools that back DRBD volumes:

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- linstor storage-pool list
----

.Sample output
[source,text]
----
╭──────────────────────────────────────────────────────────────────────────────────────────────────────╮
│ StoragePool          │ Node   │ Driver   │ PoolName                  │ FreeCapacity │ TotalCapacity │
╞══════════════════════════════════════════════════════════════════════════════════════════════════════╡
│ DfltDisklessStorPool │ node-1 │ DISKLESS │                           │              │               │
│ DfltDisklessStorPool │ node-2 │ DISKLESS │                           │              │               │
│ DfltDisklessStorPool │ node-3 │ DISKLESS │                           │              │               │
│ lvm-thin             │ node-1 │ LVM_THIN │ linstor_lvm-thin/lvm-thin │    49.89 GiB │     49.89 GiB │
│ lvm-thin             │ node-2 │ LVM_THIN │ linstor_lvm-thin/lvm-thin │    49.89 GiB │     49.89 GiB │
╰──────────────────────────────────────────────────────────────────────────────────────────────────────╯
----

Every node has a `DfltDisklessStorPool` (DRBD can always create a diskless resource anywhere).
The key is which nodes *also* have an `lvm-thin` pool -- those are the primary nodes with real EBS-backed storage.

[cols="1,1,2"]
|===
| Pool | Driver | Meaning

| `lvm-thin`
| `LVM_THIN`
| Thin-provisioned LVM pool on an EBS volume.
Thin provisioning lets LINSTOR overcommit storage -- space is allocated on write, not at PVC creation time.

| `DfltDisklessStorPool`
| `DISKLESS`
| The node can host diskless resources (quorum voters, tie-breakers) but stores no data locally.
|===

In your TNA cluster:

* The 2 nodes with `lvm-thin` pools (~50 GiB each) are the *primary nodes*.
* The node with *only* `DfltDisklessStorPool` is the *arbiter* -- it votes in DRBD quorum decisions but holds no data.

== Step 4: Examine StorageClasses

Review the pre-created StorageClasses:

[source,bash,role=execute,subs="attributes+"]
----
oc get sc
----

.Sample output
[source,text]
----
NAME                            PROVISIONER              RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
linbit-rwo-locality (default)   linstor.csi.linbit.com   Delete          WaitForFirstConsumer   true                   3h
linbit-rwx-virt                 linstor.csi.linbit.com   Delete          Immediate              true                   3h
----

You should find at least two LINSTOR-backed classes:

[cols="1,2,1"]
|===
| StorageClass | Purpose | Binding Mode

| `linbit-rwo-locality`
| Topology-aware RWO for databases -- pod and primary replica land on the same node
| `WaitForFirstConsumer`

| `linbit-rwx-virt`
| Block RWX for VM live migration with `allow-two-primaries`
| `Immediate`
|===

Inspect the parameters on the locality class:

[source,bash,role=execute,subs="attributes+"]
----
oc get sc linbit-rwo-locality -o yaml
----

.Key section from the output
[source,yaml]
----
parameters:
  autoPlace: "2"
  csi.storage.k8s.io/fstype: xfs
  property.linstor.csi.linbit.com/DrbdOptions/Resource/on-no-quorum: io-error
  property.linstor.csi.linbit.com/DrbdOptions/auto-quorum: io-error
  storagePool: lvm-thin
provisioner: linstor.csi.linbit.com
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
----

Look for these key parameters:

[cols="1,2"]
|===
| Parameter | Why it matters

| `volumeBindingMode: WaitForFirstConsumer`
| LINSTOR waits until a pod is scheduled before provisioning.
This lets the affinity controller co-locate the DRBD primary with the consumer pod, avoiding network hops for reads.

| `autoPlace: "2"`
| Create 2 diskful replicas.
On a 3-node TNA cluster the third node automatically becomes a diskless quorum voter.

| `auto-quorum: io-error`
| DRBD automatically determines quorum based on replica count.
If a node loses the majority, it returns I/O errors instead of risking split-brain writes.

| `on-no-quorum: io-error`
| When quorum is lost, the surviving minority stops accepting writes.
This prevents data divergence and is the safe default for edge deployments.

| `fstype: xfs`
| Volumes are formatted with XFS, which supports online grow and is the RHEL default.
|===

== Step 5: Create a Test PVC

Provision a test volume to see the LINSTOR provisioning cycle:

[source,bash,role=execute,subs="attributes+"]
----
cat <<'EOF' | oc apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: test-linstor-pvc
  namespace: {workshop_namespace}
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: linbit-rwo-locality
  resources:
    requests:
      storage: 1Gi
EOF
----

Check the PVC status:

[source,bash,role=execute,subs="attributes+"]
----
oc get pvc test-linstor-pvc -n {workshop_namespace}
----

.Expected output (Pending is correct at this stage)
[source,text]
----
NAME               STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS          AGE
test-linstor-pvc   Pending                                      linbit-rwo-locality   5s
----

NOTE: Because `linbit-rwo-locality` uses `volumeBindingMode: WaitForFirstConsumer`, the PVC stays `Pending` until a pod references it.
This is by design -- LINSTOR delays provisioning to co-locate the primary replica with the consumer pod.

Create a consumer pod to trigger binding:

[source,bash,role=execute,subs="attributes+"]
----
cat <<'EOF' | oc apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: test-pvc-consumer
  namespace: {workshop_namespace}
spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: consumer
      image: registry.access.redhat.com/ubi9/ubi-minimal:latest
      command: ["sleep", "300"]
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: test-linstor-pvc
EOF
----

Watch the PVC bind:

[source,bash,role=execute,subs="attributes+"]
----
oc get pvc test-linstor-pvc -n {workshop_namespace} -w
----

.Expected output (watch until STATUS changes to Bound)
[source,text]
----
NAME               STATUS    VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS          AGE
test-linstor-pvc   Pending                                                                        linbit-rwo-locality   10s
test-linstor-pvc   Bound     pvc-1405c6a1-21fc-417a-91f7-3999495777ba   1Gi        RWO            linbit-rwo-locality   15s
----

Press `Ctrl+C` once the PVC shows `Bound`.

== Step 6: Inspect the DRBD Resource

View the DRBD resource that LINSTOR created for the PVC:

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- linstor resource list
----

.Sample output
[source,text]
----
╭────────────────────────────────────────────────────────────────────────────────────────────────╮
│ ResourceName                             │ Node   │ Layers       │ Usage  │ Conns │ State    │ Vote │
╞════════════════════════════════════════════════════════════════════════════════════════════════╡
│ pvc-1405c6a1-21fc-417a-91f7-3999495777ba │ node-1 │ DRBD,STORAGE │ InUse  │ Ok    │ UpToDate │ Yes  │
│ pvc-1405c6a1-21fc-417a-91f7-3999495777ba │ node-2 │ DRBD,STORAGE │ Unused │ Ok    │ UpToDate │ Yes  │
│ pvc-1405c6a1-21fc-417a-91f7-3999495777ba │ node-3 │ DRBD,STORAGE │ Unused │ Ok    │ Diskless │ Yes  │
╰────────────────────────────────────────────────────────────────────────────────────────────────╯
----

Look at the columns:

[cols="1,2"]
|===
| Column | What to look for

| *Usage*
| `InUse` = this node is actively serving I/O to the consumer pod. `Unused` = replica exists but no local consumer.

| *State*
| `UpToDate` = diskful replica fully synced. `Diskless` = quorum voter with no local data.

| *Vote*
| `Yes` on all three nodes means DRBD has a 3-way quorum. Any two nodes agreeing can continue serving I/O -- this is how TNA survives a single node failure.

| *Conns*
| `Ok` means the replication links between nodes are healthy.
|===

In your output you should see:

* 1 node with `InUse` + `UpToDate` -- the primary, co-located with the consumer pod
* 1 node with `Unused` + `UpToDate` -- the secondary diskful replica
* 1 node with `Unused` + `Diskless` -- the arbiter, voting but storing nothing
