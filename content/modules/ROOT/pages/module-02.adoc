= Module 2: Database Locality and Performance
:navtitle: 2. Database Performance

[sidebar]
****
*Duration:* 45 minutes +
*Objective:* Demonstrate how `WaitForFirstConsumer` guarantees data locality and how DRBD delivers near-bare-metal read performance.
****

== Introduction

Traditional CSI drivers bind a PVC as soon as it is created, which can place the data volume on a different node than the pod.
LINSTOR's `WaitForFirstConsumer` binding mode delays provisioning until the pod is scheduled, ensuring the primary DRBD replica lives on the *same node* as the consumer.
Reads go directly to local block storage -- no network hop.

In this module you will deploy a PostgreSQL database, verify data locality, and use pgbench to measure the performance difference between local reads and synchronously replicated writes.

== Step 1: Deploy and Examine the PostgreSQL Database

Deploy a PostgreSQL StatefulSet that uses the `linbit-rwo-locality` StorageClass:

  name: sample-db
  namespace: {workshop_namespace}
  labels:
    app: sample-db

  serviceName: sample-db
  replicas: 1
  selector:
    matchLabels:
      app: sample-db
  template:
    metadata:
      labels:
        app: sample-db
    spec:
      securityContext:
        runAsNonRoot: true
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: postgres
          image: registry.redhat.io/rhel9/postgresql-16:latest
          env:
            - name: POSTGRESQL_USER
              value: workshopuser
            - name: POSTGRESQL_PASSWORD
              value: workshop123

== Step 2: Verify Data Locality

Confirm the PVC is bound:

[source,bash,role=execute,subs="attributes+"]
----

----

.Expected output

Now check the LINSTOR resource to confirm the primary (diskful, InUse) replica is on the same node as the pod:

│ ResourceName                             │ Node   │ Layers       │ Usage  │ Conns │ State    │ Vote │

│ pvc-542487aa-2a4e-43ef-a156-e3b8d45e8e2a │ node-1 │ DRBD,STORAGE │ InUse  │ Ok    │ UpToDate │ Yes  │
│ pvc-542487aa-2a4e-43ef-a156-e3b8d45e8e2a │ node-2 │ DRBD,STORAGE │ Unused │ Ok    │ UpToDate │ Yes  │

This is the `WaitForFirstConsumer` mechanism in action: LINSTOR delayed provisioning until the pod was scheduled, then placed the primary DRBD replica on the same node.
Reads from PostgreSQL go directly to local block storage with zero network hops.

[source,text]
----

transaction type: <builtin: TPC-B (sort of)>
scaling factor: 10
query mode: simple
number of clients: 4
number of threads: 2
maximum number of tries: 1
duration: 30 s

number of failed transactions: 0 (0.000%)
latency average = 2.708 ms
initial connection time = 4.378 ms
tps = 1477.367478 (without initial connection time)
----

Compare your results:

[cols="1,1,1,2"]
|===
| Workload | TPS | Avg Latency | Why

| Select-only (Step 3)
| ~31,750
| ~0.13 ms
| Reads served from local DRBD primary -- no network hop

| Mixed TPC-B (Step 4)
| ~1,477
| ~2.71 ms
| Each write must replicate to the remote peer and wait for acknowledgment before returning
|===

The ~21x TPS difference and ~21x latency increase demonstrate DRBD's *synchronous replication cost*.
Reads are essentially bare-metal speed because `WaitForFirstConsumer` placed the primary replica on the same node as PostgreSQL.
Writes pay the network round-trip penalty because DRBD protocol C requires the remote peer to confirm every write before the application sees success.

== Step 5: Understand DRBD Replication Protocol

Examine the DRBD resource-definition properties for the database PVC:

[source,bash,role=execute,subs="attributes+"]
----
PV_NAME=$(oc get pvc data-sample-db-0 -n {workshop_namespace} -o jsonpath='{.spec.volumeName}')
oc exec -n {linbit_namespace} deploy/linstor-controller -- linstor resource-definition list-properties "$PV_NAME"
----

.Sample output
[source,text]
----
╭───────────────────────────────────────────────────────────╮
│ Key                                  │ Value              │
╞═══════════════════════════════════════════════════════════╡
│ Aux/csi-provisioning-completed-by    │ linstor-csi/1.12.0 │
│ Aux/csi.storage.k8s.io/pvc/name      │ data-sample-db-0   │
│ Aux/csi.storage.k8s.io/pvc/namespace │ linbit-workshop    │
│ DrbdOptions/Resource/quorum          │ majority           │
│ DrbdOptions/auto-verify-alg          │ sha256             │
╰───────────────────────────────────────────────────────────╯
----

Notice that *protocol C* does not appear in the properties -- it is the DRBD default and doesn't need to be explicitly set.
DRBD has three replication protocols:

[cols="1,1,2"]
|===
| Protocol | Type | When write returns

| *A*
| Asynchronous
| As soon as the local write completes (remote may lag)

| *B*
| Semi-synchronous
| After the remote node receives the data in memory (not yet on disk)

| *C* (default)
| Synchronous
| After the remote node confirms the write is on disk
|===

Protocol C is the safest -- a crash on either node cannot lose acknowledged data.
The tradeoff is the write latency you observed in Step 4: every PostgreSQL commit must wait for a network round-trip to the peer node.

Also note `quorum: majority` -- on your 3-node TNA cluster, any 2 of 3 nodes must agree for writes to proceed.
This prevents split-brain at the cost of requiring at least 2 nodes to be reachable.

== Step 6: Verify Replication Topology

Examine the DRBD resource backing the database with volume-level detail:

[source,bash,role=execute,subs="attributes+"]
----
oc exec -n {linbit_namespace} deploy/linstor-controller -- linstor resource list-volumes
----

.Sample output
[source,text]
----
╭──────────────────────────────────────────────────────────────────────────────────────────────────────────────────╮
│ Resource                                 │ Node   │ StoragePool          │ VolNr │ DeviceName    │ Allocated  │ InUse  │ State    │ Repl           │
╞══════════════════════════════════════════════════════════════════════════════════════════════════════════════════╡
│ pvc-542487aa-...                         │ node-1 │ lvm-thin             │     0 │ /dev/drbd1000 │ 341.77 MiB │ InUse  │ UpToDate │ Established(2) │
│ pvc-542487aa-...                         │ node-2 │ lvm-thin             │     0 │ /dev/drbd1000 │ 334.08 MiB │ Unused │ UpToDate │ Established(2) │
│ pvc-542487aa-...                         │ node-3 │ DfltDisklessStorPool │     0 │ /dev/drbd1000 │            │ Unused │ Diskless │ Established(2) │
╰──────────────────────────────────────────────────────────────────────────────────────────────────────────────────╯
----

This view shows additional detail compared to `resource list`:

[cols="1,2"]
|===
| Column | Meaning

| *StoragePool*
| `lvm-thin` = diskful replica on real storage. `DfltDisklessStorPool` = diskless quorum voter.

| *Allocated*
| Actual space consumed on the thin pool. Compare this against the 5 GiB PVC request -- thin provisioning means only written data takes space.

| *Repl*
| `Established(2)` = this node has active replication connections to 2 other nodes.
|===

On your TNA cluster you see:

* 2 diskful replicas (`UpToDate`) on the primary nodes -- writes replicate synchronously between them
* 1 diskless voter (`Diskless`) on the arbiter -- participates in quorum votes but does not add replication latency

== Summary

In this module you:

* Deployed a PostgreSQL database on `linbit-rwo-locality` and confirmed `WaitForFirstConsumer` co-located the pod and primary DRBD replica on the same node
* Measured local-read performance (~31,750 TPS at 0.13 ms latency) -- near-bare-metal speed with zero network hops
* Measured mixed read/write performance (~1,477 TPS at 2.71 ms latency) and identified synchronous replication as the write bottleneck
* Learned that DRBD protocol C (the default) requires remote acknowledgment on every write -- the safest option but with a latency tradeoff
* Examined the TNA replication topology: 2 diskful replicas for data safety + 1 diskless voter for quorum, with the arbiter adding zero write latency

You can now explain why `WaitForFirstConsumer` is critical for database performance at the edge and articulate the read/write latency tradeoff of synchronous replication.
